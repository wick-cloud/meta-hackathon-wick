# Security boundaries and verification coverage

This inventory describes the application boundaries and the tests that exercise them. Test evidence establishes the behavior of those cases; it is not an exhaustive penetration test or a security certification. Deployment, upstream services, dependency updates, and new routes require continuing review.

## Untrusted execution and external services

Coding jobs accept only anonymous public GitHub repositories and pinned commits. Metadata requests use the fixed GitHub API origin and reject redirects. The model can propose validated read/write/test/finish actions; it cannot select arbitrary executable tools or gain funding authority. The frozen test command runs in the customer VM's bubblewrap sandbox after an isolation probe. Studio can bootstrap fixed OS packages before that probe. Repository code is not executed in the Broker server process.

[Repository and model action tests](../tests/coding.test.ts), [guest file tests](../tests/coding-guest-files.test.ts), [command envelope tests](../tests/coding-command.test.ts), and [coding lifecycle tests](../tests/coding-db.test.ts) cover permitted actions, foreign repository origins, private repositories, traversal/symlinks, replay, quota, and deadline enforcement. [The opt-in Linux runner](../tests/coding-local-e2e.ts) exercises actual guest isolation separately from ordinary unit tests. Workspace size is monitored, so temporary overshoot is possible; per-process limits are not aggregate cgroup quotas. Native provider behavior still requires its own qualification.

The anonymous guided Studio demo has a fixed Hello World task, separate from signed-in repository work. It accepts only a single literal `print` expression after Python AST validation, then executes those validated bytes in the visitor's VM with bounded time, output, and process resources. Its user-writable journal cannot authorize execution or supply a trusted result. [Guided runner tests](../tests/demo-studio.test.ts), [demo ownership and budget tests](../tests/demo-studio-db.test.ts), and [execution/recovery tests](../tests/demo-studio-execution-db.test.ts) cover this narrower boundary.

Muse output is untrusted data: schemas, approved catalog choices, server pricing, and provider policy constrain its effect. Bounded requests/responses and timeouts limit adapter work. [Muse tests](../tests/muse.test.ts), [provider identity tests](../tests/provider-identity-routes.test.ts), and [inference adapter tests](../tests/inference-adapters.test.ts) cover accepted responses and malformed, oversized, off-policy, or uncertain outcomes. Prompt instructions and credential redaction are additional controls, not substitutes for these checks.

Service credentials remain server-side. Wick HTTP requests stay within the operator-configured HTTPS API base and reject redirects; Muse's API base is also operator configuration. Inference routes use fixed provider endpoints. See [Wick transport tests](../tests/wick-contract.test.ts) and [inference adapter tests](../tests/inference-adapters.test.ts).

The upstream terminal destination is a **trusted Wick session API response**, not a browser-supplied URL. The connector requires credential-free `wss:`, rejects query/fragment components and redirects, and sends only a scoped terminal token. It does not enforce a terminal hostname allowlist, DNS pinning, or a general private-address denylist. This boundary assumes the configured Wick service returns legitimate terminal destinations; changing that policy requires evidence for supported provider endpoints.

## Ingress and resource limits

`AUTH_TRUST_RAILWAY_PROXY=true` assumes every relevant request arrives through Railway's public HTTP edge, which supplies the trusted `X-Real-IP`. Private/internal or direct ingress must not accept that header as authoritative. With proxy trust disabled, the application derives the address from the socket and ignores client forwarding headers, including when forwarding requests to Better Auth.

Preauthentication admission bounds database work before credential verification: 1,200 API requests and 300 mutations per minute per address; auth paths have separate 60/20 limits. Concurrent HTTP admission is capped at 64 per address and 256 globally. Authenticated accounts share 600 requests/120 writes per minute across keys and sessions; individual keys retain their 300/60 limits. Repository verification permits 12 attempts per owner per minute, two concurrent preparations per owner, and eight globally, with early capacity checks before GitHub access.

These counters are **process-local** and reset on restart. They assume the documented single application replica; multiple replicas require coordinated enforcement. Database transaction limits still govern funding and resource admission. Shared networks may share an IP budget. [Request admission tests](../tests/request-limits.test.ts), [account budget tests](../tests/developer-keys-auth.test.ts), [authentication tests](../tests/auth.test.ts), and [preparation tests](../tests/coding-preparation.test.ts) cover invalid keys, header spoofing, concurrency, release, combined account budgets, and full-capacity rejection.

## Scope of the aggregate route check

[The anonymous route test](../tests/route-auth-boundary.test.ts) discovers more than 100 registered business routes across marketplace, orders, agreements, key management, inference, coding, Studio, disks, Muse, and negotiation. Each representative request must reach the authentication guard, return 401, and avoid database/provider operations. New routes inside these registrars are included automatically; a separate registrar must be added explicitly.

That test uses a rejecting authentication stub. It does not prove successful authentication, every request shape, every role/scope combination, or complete multi-tenant isolation. Those properties rely on the targeted tests linked above and further adversarial review. Authentication endpoints, public documentation/downloads/health, the anonymous demo, and WebSocket upgrades are outside this aggregate test and have separate coverage. Database suites require a disposable `TEST_DATABASE_URL`; skipped suites must not be reported as passing. Live provider calls, paid resource allocation, and a production deployment are not implied by offline test success.
